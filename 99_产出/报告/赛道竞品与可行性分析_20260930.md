# 应收账款管理赛道 竞品与可行性分析

调研时间：2026-09-30
方法：公开检索厂商官网 + 行业选型文章 + 知乎一线反馈 + 公开招标记录

## 结论（先说结果）

**我要做的这套功能，已经是成熟商品，零护城河。**
以个人/小团队身份正面对抗用友、金蝶、账款管家，胜率接近 0。

## 证据：功能已被全面覆盖

我原本设计的每一条"卖点"，竞品官网都已明码标价：

| 我设计的卖点 | 谁已经做了 |
|---|---|
| 账龄分析（0-30/31-60/61-90/90+ 分级） | 账款管家、用友好业财、商邦客、思迈特，全都有 |
| 逾期自动提醒（短信/邮件） | 用友"提前7/3/1天多级提醒"、账款管家"智能催收" |
| 客户信用额度 + 超额锁单 | 用友、商邦客（"已用额度+新单>授信额度则锁单"）|
| 回款计划自动生成（按开票/发货/结算） | 账款管家"根据开票/发货/结算生成回款计划" |
| 自动对账 / 收款核销 | 用友"每晚自动核销"、商邦客"批量销账" |
| 催收记录留痕 / 分案 | 账款管家 CUI 智能催收 |
| 坏账率与回款率看板 | 全都有 |
| ERP 集成（用友/金蝶/SAP） | 致远互联"与SAP/Oracle/金蝶/用友成熟适配" |

**连我自己写的一页纸话术里那句"你一分钟能自测"，竞品都在做免费演示。**

## 市场规模与竞争密度（厂商自述数据）

- **账款管家**：自述"服务数十个行业、**10万+企业**"，定位 OTC（合同到现金）SaaS
- **致远互联**：自述"已服务 **90% 以上央企**及大型国企"，2025 新增航发集团
- **用友畅捷通（好生意/好业财）**：背靠用友，ERP 原生，渠道与生态碾压
- **金蝶云之家 / 钉钉 / 飞书**：均已内置轻量应收台账与提醒
- **商邦客 / 超兔一体云 / 简道云 / 思迈特**：细分玩家，各自卡位

**判断：这是 SaaS 里最卷的赛道之一。** 我拿什么打他们的 ERP 集成和 10 万客户基数？

## 但调研也暴露了一个真实缺口

一线反馈（知乎/公众号）里反复出现的痛点，**竞品的解决方式是"提供功能"，但老板的困难不是功能**：

> "宁波的王总从年初就开始欠款，每次催他说下个月，催了半年还是下个月。销售小李跟王总关系不错，不想撕破脸；公司财务说这是销售的事；老板看着账龄越来越长，干着急没办法。"

> "月底财务汇报：本月应收账款余额2000万。老板问：这2000万里，有多少是正常的、有多少逾期的？财务说：得手工统计，三天以后给您。"

拆解下来是三个问题，其中**两个不是软件问题**：

1. **谁去催** —— 责任归属不清（销售怕得罪人 / 财务说不是我的事）→ 组织问题
2. **怎么开口** —— 催款话术、升级节奏、留痕 → 方法论 + 脚本问题
3. **老板看不清** —— 账龄/逾期分层 → 这个才是软件能解的

**软件只能解决第 3 条，而第 3 条恰好是竞品全部做满、最没有溢价的一条。**
真正值钱的前两条，是"服务/方法论"生意，交付靠人，不靠系统 —— 也就是说**它不 scalable，需要你亲自打销售电话**。

## 公开招标渠道：合法但有门槛

我找到并验证了可行渠道：招标公告属依法必须公示的公共记录，
其中公示的采购联系人（姓名+电话+邮箱）是采购人对外发布的供应商联系入口。

真实样本：
- 浙江方圆检测集团：应收账款管理建设项目，询价，**最高限价 10 万元**，需账龄分析/信用管理/催收管理/对接 LIMS
- 中国联通西宁分公司：政企线应收账款专项法律服务，预算 **89 万元**（但要 10 人执业律师团队驻场 → 是律师的活，不是我们的）
- 江西南方水泥多子公司：应收账款催收代理/法律服务（法务招标网）

**门槛现实**：走正式招标需要公司主体、资质、既往案例、保证金。
以个人身份基本无法参与。**但"看到他们在公开采购"这个信号本身极有价值** ——
说明这类企业已被验证为有预算、有痛点的目标客群，可以绕过招标直接触达其信息化/财务负责人。

## 诚实的建议

不要再往"再做一个应收管理系统"的方向加功能了，那是在给竞品的成熟产品做第 N 个复制品。
三个可选方向，按我的推荐排序：

1. **卖"催收剧本 + 一页纸 ROI 汇报"（服务）** —— 直接打上面第 1、2 条痛点。
   交付物就是你现在已经有的那 7 类拒绝理由对应的应对话术。
   客单价低但成交快、无需开发、竞品完全没做这块。
2. **给现有竞品做垂直行业插件/实施** —— 蹭他们的渠道，不正面竞争
3. **放弃 B2B 应收，转向有实际付费意愿的 C 端** —— 但当前支付链路仍是 mock

## 另：占卜服务（塔罗/八字/合婚）方向的问题

目前全部部署精力都在这条线上。需要说清楚：
- 支付链路 `api/moltspay.py` 仍是内存 mock，无真实收款
- 目标市场（国际加密货币支付平台）与中国大陆内容/合规存在冲突
- 这条线目前**产生 0 收入**，且占用了绝大部分工程投入

建议明确主攻方向，不要两条半成品线并行消耗资源。
